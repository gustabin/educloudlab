# LAB-010: End-to-end retail analytics capstone (release 1.3)

Breakdown written before starting, as master plan §29 requires. The capstone adds **no new platform code**: it combines features that already exist (ingestion, pipelines, transforms, the star-schema checks, the semantic model and dashboards) and is graded only with the existing closed set of checks (ADR-008).

## Design

- **Flow (master plan §28):** CSV → raw → bronze → silver (cleaning) → gold (`dim_customer`, `dim_product`, `dim_store`, `dim_date`, `fact_sales`) → semantic model → dashboard.
- **Metrics:** revenue, orders, customers, AOV; revenue by region, by product and by month.
- **Setup:** a lakehouse and the five retail samples in the **raw** layer only. Ingestion is the student's first task.
- **Cleaning:** uses the generator's deliberate defects:
  - 30 duplicated customers with unnormalised emails;
  - 40 customers without email, who must be kept because they have orders;
  - about 5 % cancelled orders.
- **Notebooks:** not required (no `requires`), so the capstone runs on every install. Notebook exploration is suggested but not graded.
- **Difficulty:** advanced. The instructions state *what* is expected, and the hints carry the *how* (with penalties).

## Tasks

| Task | Points | Checks |
|---|---|---|
| t1 Ingestion raw → bronze | 10 | `dataset_exists` ×5; `row_count` on customers (1,030, defects kept) and order_items |
| t2 Customer-cleaning pipeline | 20 | `pipeline_has_nodes` (source, sql, quality_check, output); `pipeline_run_succeeded` → `silver.customers`; unique ids; every customer kept; emails normalised |
| t3 `silver.sales` | 15 | columns; `value_range`; count and total vs. completed order lines |
| t4 Dimensions | 10 | columns, unique surrogate keys, `full_date` DATE |
| t5 Fact table | 15 | `references` ×4; no null customer key; count and total; revenue by category |
| t6 Semantic model `retail` | 15 | `semantic_model_has`: fact table, 4 relationships, 4 measures, 4 dimensions (month grain) |
| t7 Dashboard `panel-retail` | 15 | `dashboard_has_widgets`: 4 KPIs, bar by region, table by product, line by month, region filter |

The schema allows at most 10 checks per task, which is why the star schema is split between t4 and t5.

## Acceptance criteria

- The lab validates against `lab.schema.json` and imports cleanly.
- The reference solution scores 100 and an empty attempt scores 0 (`LabSolutionsTest`).
- A negative test covers the typical mistakes and checks that each feedback names the problem. The mistakes are: dropping customers without email, counting cancelled orders, and counting orders as customers.
- Lab counts are updated (catalog, public site, definition tests). The public description is in `docs/labs/LAB-010.md`.
- `composer check`, pytest and `npm run e2e` are green.
