# M8: Notebooks in a Docker sandbox (release 1.3)

Granular breakdown written before starting, as master plan §29 requires. Decisions follow ADR-005 (queue + dispatcher), ADR-006 (DuckDB lakehouse) and **ADR-010**:
- student Python runs only inside an ephemeral Docker container;
- notebooks stay in a read-only demonstration mode until the isolation suite passes.

This is the only milestone that runs arbitrary student code, so its security gate is release-blocking (master plan risk R3).

## Concepts

- **Notebook:** a resource of type `notebook` (already in the `resources.type` ENUM). Its definition is an ordered list of cells, each `markdown` or `code`, with at most 50 cells of 20,000 characters each.
- **Run:** a `notebook_run` job executes **all code cells in order** in one fresh container. It stores, per cell, the stdout/stderr text (truncated), the repr of the last expression, pandas DataFrames as bounded tables, and the error type and message.
  - There is no persistent kernel: every run starts from scratch. This is simpler and safer than an interactive kernel, and enough for the labs.
- **Data access inside the container:**
  - A **copy** of the workspace lakehouse is mounted read-only at `/data/lakehouse.duckdb`.
  - `duckdb` and `pandas` are available, and `lakehouse()` opens a read-only connection.
  - Students do not write to the lakehouse. `save_result(name, dataframe)` records a bounded artifact (at most 1,000 rows) in the run.
- **Sandbox:** `app/Modules/Notebooks/DockerSandbox.php`, launched by the dispatcher with `proc_open` and an argument array, never a shell.
  - Flags:
    - `docker run --rm --network none --read-only --tmpfs /tmp:rw,size=64m`
    - `--memory 512m --memory-swap 512m --cpus 1 --pids-limit 128 --ulimit nofile=256:256`
    - `--cap-drop ALL --security-opt no-new-privileges --user 10001:10001`
  - Mounts: the lakehouse copy (read-only) and an input/output directory per run (outside the workspace).
  - No environment variables from the host.
  - A wall-clock timeout, after which the dispatcher runs `docker kill <name>`.
  - The output file is size-capped and parsed as JSON only.
- **Image:** `educloud-nb:1`, built from `worker/notebook/Dockerfile` with `php scripts/notebook-image.php build`. It contains:
  - `python:3.11-slim`;
  - duckdb, pandas and pyarrow, pinned with hashes;
  - the executor `nb_exec.py`;
  - a non-root user.
- **Feature flag:** `NOTEBOOKS_MODE` = `off | demo | docker` (default `demo`).
  - In `demo` mode notebooks can be created and edited, but **Run** answers 409 `NOTEBOOKS_DISABLED`.
  - `docker` mode needs the daemon and the image, as checked by `scripts/check-env.php`.

## Non-goals

- Interactive kernels, widgets, package installation by students, GPU and Spark.
- Writing to the lakehouse from notebooks (artifacts only).
- JupyterHub (master plan "Future").

## Risks

| Risk | Mitigation |
|---|---|
| Container escape / host access | Docker Desktop isolation (WSL2 VM). No network, a read-only root filesystem, no capabilities, `no-new-privileges`, a non-root user and minimal mounts. The release-blocking isolation suite. The web server never talks to the daemon; only the dispatcher does. |
| Resource exhaustion | Memory, CPU, pids and nofile limits; a tmpfs size cap; a wall-clock timeout with kill; output caps; the active-jobs quota; a single dispatcher. |
| Docker not running on a machine | `demo` mode by default, check-env diagnostics, the suite skips with a clear reason, and LAB-008 cannot be run. |
| Data leakage between workspaces | Only the job's own lakehouse **copy** is mounted. The run directory is unique and is deleted afterwards. |
